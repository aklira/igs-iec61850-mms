# F4 — Interop bench skeleton

## Prompt

Run task F4 of `IMPLEMENTATION.md`.

## Summary

`bench/` follows the bench of `igs-iso9506-mms`: the same compose wrapper, capture and tshark helpers,
and the same reference peer (libiec61850 `v1.6.2.1`, commit `c28c27c`, built locally as
`localhost/igs61850-peer:v1.6.2.1`; the image is identical to the MMS one). The reference server is an
example IEC 61850 server of the peer, chosen by `REF_SERVER` (default `server_example_basic_io`),
published on `127.0.0.1:11102`.

Scenario `tests/test_f4_mms_client.py`: the `igsmms-client` of `igs-iso9506-mms`, built from its
current commit and run on the host, identifies the server and lists its logical devices; the capture
decodes without malformed frame or error (the zero-byte MMS artefact of the release is filtered, as in
the MMS bench). The IEC 61850 profile of the MMS crates comes with N2, so the client runs with nesting
level 6 and the lenient parameter CBBs (MMS gap G8).

Observed: the listing of the variables of the logical device `simpleIOGenericIO` fails. The server
answers in one PDU of 7721 octets whose identifiers reach 39 characters (for example the
`TimeofEntry` attribute of a buffered report control block); the MMS stack, capped at 32, aborts the
association. The scenario is kept as a strict expected failure until task N1 (MMS-001). Each command
also waits about 15 s for a release the server does not confirm (MMS gap G1).

Edition 1 server mode (for task E3): the user documentation of libiec61850 does not mention an edition
setting, and no example binary exposes one. The question stays open for E3; reading the source to find
out is not allowed (rule 1).

Result: 1 passed, 1 expected failure.
